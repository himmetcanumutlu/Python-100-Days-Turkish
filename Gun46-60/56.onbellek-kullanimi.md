## Önbellek Kullanımı

> **Translated to Turkish by** himmetcanumutlu

Genellikle Web uygulamalarının performans darboğazı ilişkisel veritabanında ortaya çıkar; eş zamanlı erişim yüksek olduğunda, tüm isteklerin veri kalıcılaştırma işlemini ilişkisel veritabanıyla yapması gerekirse, veritabanı mutlaka yükün altında kalır. Web uygulamasının performansını optimize etmenin en önemli yolu önbellek kullanmaktır; veri hacmi büyük olmayan ama erişim sıklığı çok yüksek veriyi önceden önbellek sunucusuna yüklemek, tipik bir "alandan vazgeçip zaman kazanma" yöntemidir. Genellikle önbellek sunucuları veriyi doğrudan belleğe koyar ve çok verimli veri erişim stratejileri kullanır (karma depolama, anahtar-değer çifti biçimi vb.); okuma/yazma performansı ilişkisel veritabanından çok daha üstündür; bu yüzden Web uygulamasını önbellek sunucusuna bağlayıp performansını optimize edebiliriz; çok iyi seçeneklerden biri Redis kullanmaktır.

Web uygulamasının önbellek mimarisi yaklaşık olarak aşağıdaki gibidir.

### Django Projesini Redis'e Bağlama

Önceki derslerde Redis kurulumu ve kullanımını anlatmıştık; burada tekrar anlatmayacağız. Django projesinde Redis'e bağlanmak gerekirse üçüncü taraf `django-redis` kütüphanesi kullanılabilir; bu üçüncü taraf kütüphane, Redis'e yönelik çeşitli işlemleri kapsülleyen `redis` adlı üçüncü taraf kütüphaneye bağımlıdır.

`django-redis` kurulumu.

```Bash
pip install django-redis
```

Django yapılandırma dosyasındaki önbellek yapılandırmasını değiştirin.

```Python
CACHES = {
    'default': {
        # django-redis ile Redis hizmetine bağlanmayı belirtir
        'BACKEND': 'django_redis.cache.RedisCache',
        # Redis sunucusunun URL'si
        'LOCATION': ['redis://1.2.3.4:6379/0', ],
        # Redis'teki anahtarın ön eki (adlandırma çakışmasını çözer)
        'KEY_PREFIX': 'vote',
        # Diğer yapılandırma seçenekleri
        'OPTIONS': {
            'CLIENT_CLASS': 'django_redis.client.DefaultClient',
            # Bağlantı havuzu (önceden ayrılmış yedek Redis bağlantıları) parametresi
            'CONNECTION_POOL_KWARGS': {
                # Maksimum bağlantı sayısı
                'max_connections': 512,
            },
            # Redis'e bağlanan kullanıcı parolası
            'PASSWORD': 'foobared',
        }
    },
}
```

Bu noktada Django projemiz Redis'e bağlanabilir; şimdi proje kodunu değiştirip Redis'i, ders verisi alan arayüz için önbellek hizmeti sağlamakta kullanalım.

### Görünüme Önbellek Hizmeti Sağlama

#### Bildirimsel Önbellek

Bildirimsel önbellek, asıl kodu değiştirmeden Python'daki dekoratör (vekil) ile mevcut koda önbellek işlevi eklemektir. FBV için kod aşağıdaki gibidir.

```Python
from django.views.decorators.cache import cache_page


@api_view(('GET', ))
@cache_page(timeout=86400, cache='default')
def show_subjects(request):
    """Ders verisini alır"""
    queryset = Subject.objects.all()
    data = SubjectSerializer(queryset, many=True).data
    return Response({'code': 20000, 'subjects': data})
```

Yukarıdaki kod, Django'nun kapsüllediği `cache_page` dekoratörüyle görünüm fonksiyonunun dönüş değerini (yanıt nesnesini) önbelleğe alır; `cache_page`'in asıl amacı görünüm fonksiyonunun render ettiği sayfayı önbelleğe almaktır; JSON verisi döndüren görünüm fonksiyonları için JSON verisini önbelleğe almak gibidir. `cache_page` dekoratörü kullanılırken, önbellek süre sonunu belirtmek için `timeout` parametresi, veriyi önbelleğe almak için hangi önbellek hizmet grubunun kullanılacağını belirtmek için `cache` parametresi geçilebilir. Django projesi, yapılandırma dosyasında birden çok önbellek hizmet grubu yapılandırmaya izin verir; yukarıdaki `cache='default'`, varsayılan önbellek hizmetini kullanmayı belirtir (çünkü önceki yapılandırma dosyasında yalnızca `default` adlı önbellek hizmetini yapılandırmıştık). Görünüm fonksiyonunun dönüş değeri bayt dizisine serileştirilip Redis'e konur (Redis'teki str tipi bayt dizisi alabilir); önbellek verisinin serileştirme ve serileştirmeden çıkarılmasını da kendimiz yapmamız gerekmez; çünkü `cache_page` dekoratörü, Redis'e bağlanmak için `django-redis` kütüphanesindeki `RedisCache`'i çağırır; bu sınıf Redis'e bağlanmak için `DefaultClient` kullanır ve [pickle serileştirme](https://python3-cookbook.readthedocs.io/zh_CN/latest/c05/p21_serializing_python_objects.html) kullanır; `django_redis.serializers.pickle.PickleSerializer` varsayılan serileştirme sınıfıdır.

Önbellekte ders verisi yoksa, arayüzden ders verisine erişildiğinde görünüm fonksiyonumuz `Subject.objects.all()` çalıştırıp veritabanına SQL göndererek veriyi alır; görünüm fonksiyonunun dönüş değeri önbelleğe alınır; bu yüzden bir sonraki istekte önbelleğin süresi dolmamışsa doğrudan önbellekten alınır, veritabanını yeniden sorgulamak gerekmez. Önbelleğin kullanımını görmek istiyorsanız veritabanı logunu yapılandırabilir veya Django-Debug-Toolbar ile görüntüleyebilirsiniz; ders veri arayüzüne ilk erişimde ders verisini sorgulayan SQL deyimini görürsünüz; ders verisini yeniden alırken veritabanına SQL gönderilmez; çünkü veri doğrudan önbellekten alınabilir.

CBV için, Django'daki `method_decorator` adlı dekoratörle `cache_page` dekoratörünü sınıftaki metoda koyabiliriz; etki yukarıdaki kodla aynıdır. Hatırlatmak isteriz ki `cache_page` dekoratörü doğrudan sınıfa konamaz; çünkü fonksiyon süsleyen bir dekoratördür; Django framework'ü bu sorunu çözmek için `method_decorator`'ü sunar; açıkça `method_decorator` sınıf süsleyen bir dekoratördür.

```Python
from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_page


@method_decorator(decorator=cache_page(timeout=86400, cache='default'), name='get')
class SubjectView(ListAPIView):
    """Ders verisini alan görünüm sınıfı"""
    queryset = Subject.objects.all()
    serializer_class = SubjectSerializer
```

#### Programatik Önbellek

Programatik önbellek, önbellek hizmetini kendi yazdığınız kodla kullanmaktır; bu yöntemin kod miktarı biraz daha fazla olsa da, bildirimsel önbelleğe kıyasla önbelleğin işletilmesi ve kullanımı daha esnektir; gerçek geliştirmede daha çok kullanılır. Aşağıdaki kod, daha önce kullandığımız `cache_page` dekoratörünü kaldırıp `django-redis`'in sunduğu `get_redis_connection` fonksiyonuyla doğrudan Redis bağlantısı alıp Redis'i işletir.

```Python
def show_subjects(request):
    """Ders verisini alır"""
    redis_cli = get_redis_connection()
    # Önce önbellekten ders verisini almayı dener
    data = redis_cli.get('vote:polls:subjects')
    if data:
        # Ders verisi alınırsa serileştirmeden çıkar
        data = json.loads(data)
    else:
        # Önbellekte ders verisi yoksa veritabanını sorgular
        queryset = Subject.objects.all()
        data = SubjectSerializer(queryset, many=True).data
        # Bulunan ders verisini serileştirip önbelleğe koyar
        redis_cli.set('vote:polls:subjects', json.dumps(data), ex=86400)
    return Response({'code': 20000, 'subjects': data})
```

Belirtmek gerekir ki Django framework'ü, önbellek işlemini desteklemek için `cache` ve `caches` olmak üzere iki hazır değişken sunar; birincisi varsayılan önbelleğe (`default` adlı önbellek) erişir; ikincisi indeksleme işlemiyle belirtilen önbellek hizmetini alır (örneğin `caches['default']`). `cache` nesnesine `get` ve `set` mesajı göndererek önbelleğe okuma ve yazma yapılabilir; ancak bu yöntemle yapılabilecek işlemler sınırlıdır; yukarıdaki kod kadar esnek değildir. Dikkat edilmesi gereken bir nokta daha var: `get_redis_connection` fonksiyonuyla alınan Redis bağlantı nesnesiyle Redis'e `FLUSHDB`, `SHUTDOWN` gibi tehlikeli işlemler dahil çeşitli işlemler gönderilebilir; bu yüzden gerçek ticari proje geliştirmede `django-redis` genellikle yeniden kapsüllenir; örneğin yalnızca projenin ihtiyaç duyduğu önbellek işlemlerini sağlayan bir araç sınıfı kapsüllenir; böylece doğrudan `get_redis_connection` kullanmanın olası riskinden kaçınılır. Elbette önbellek işlemini kendiniz kapsülleyerek "Read Through" ve "Write Through" biçimiyle önbellek güncellemesi de yapılabilir; bu aşağıda anlatılacak.

### Önbellekle İlgili Sorunlar

#### Önbellek Verisinin Güncellenmesi

Önbellek kullanırken netleştirilmesi gereken bir sorun vardır: veri değiştiğinde önbellekteki veri nasıl güncellenir? Önbelleği güncellemenin genellikle şu yöntemleri vardır:

1. Cache Aside Pattern
2. Read/Write Through Pattern
3. Write Behind Caching Pattern

1. yöntemin somut uygulaması: veri güncellenirken önce veritabanı güncellenir, sonra önbellek silinir. Dikkat, "önce veritabanını güncelle sonra önbelleği güncelle" veya "önce önbelleği sil sonra veritabanını güncelle" biçimi kullanılamaz; nedenini kendiniz düşünün (eş zamanlı okuma ve yazma senaryosunu düşünün). Elbette "önce veritabanını güncelle sonra önbelleği sil" yaklaşımının da teorik riski vardır; ama sorun çıkma olasılığı çok düşüktür; bu yüzden birçok proje bu yöntemi kullanır.

1. yöntem, iş kodu yazan geliştiricinin iki depolama sisteminin (önbellek ve ilişkisel veritabanı) işleminden kendisinin sorumlu olmasını gerektirir; kod yazması çok zahmetlidir. 2. yöntemin özü, arka uçtaki depolama sistemini tek bir koda dönüştürmektir; önbelleğin bakımı bu kodda kapsüllenir. Read Through, önbelleği sorgu işleminde günceller; yani önbellek geçersiz olduğunda verinin yüklenmesinden önbellek hizmeti sorumludur; böylece uygulama tarafı için şeffaftır; Write Through ise veri güncellenirken önbellek isabet etmezse doğrudan veritabanını güncelleyip döner; önbellek isabet ederse önbelleği günceller, sonra önbellek hizmeti veritabanını kendisi günceller (eş zamanlı güncelleme). Az önce söylediğimiz gibi, projedeki Redis işlemini kendiniz yeniden kapsüllerseniz "Read Through" ve "Write Through" modunu gerçekleştirebilirsiniz; bu, iş yükünü artırsa da kuşkusuz "bir kez yapıp sürekli yararlanılan" ve "uzun vadeli fayda sağlayan" bir iştir.

3. yöntem, veri güncellenirken yalnızca önbelleği günceller, veritabanını güncellemez; önbellek hizmeti veritabanını **asenkron toplu günceller**. Bu yaklaşım performansı büyük ölçüde artırır; ama bedeli verinin **güçlü tutarlılığından** vazgeçmektir. 3. yöntemin gerçekleme mantığı karmaşıktır; çünkü hangi verinin güncellendiğini izleyip sonra toplu olarak kalıcı katmana yazmak gerekir.

#### Önbellek Delinmesi (Cache Penetration)

Önbellek, veritabanının yükünü hafifletmek için eklenen bir ara katmandır; kötü niyetli ziyaretçiler önbellekte olmayan veriye sık erişirse, önbellek anlamını yitirir; tüm isteklerin yükü anında veritabanına biner; bu da veritabanının büyük yük altında kalmasına, hatta bağlantı hatasına yol açar; dağıtık hizmet engelleme saldırısına (DDoS) benzer. Önbellek delinmesini çözmenin bir yolu, sorgu boş dönerse bu boş değeri de önbelleğe almaktır; ancak bu boş değerin önbelleğine kısa bir süre sonu ayarlanmalıdır; sonuçta böyle bir değeri önbelleğe almak önbellek alanını boşa harcar. Önbellek delinmesini çözmenin bir başka yolu Bloom filtresi kullanmaktır; somut yöntemi kendiniz inceleyebilirsiniz.

#### Önbellek Kırılması (Cache Breakdown)

Gerçek projede, belirli bir önbellek anahtarının belirli bir anda süresi dolabilir; ama tam o anda o anahtara çok sayıda eş zamanlı istek gelir; bu istekler önbellekte anahtarın verisini bulamayınca doğrudan veritabanından veri alıp önbelleğe yazar; bu durumda yüksek eş zamanlı istekler veritabanını anında çökertebilir; bu olguya önbellek kırılması denir. Önbellek kırılmasını çözmenin yaygın yolu karşılıklı dışlama kilidi (mutex) kullanmaktır; basitçe, önbellek geçersiz olduğunda hemen veritabanından veri yüklemek yerine önce karşılıklı dışlama kilidi kurulur (örneğin Redis'teki setnx); yalnızca kilidi başarıyla kuran istek sorguyu çalıştırıp veritabanından veri yükleyip önbelleğe yazar; kilidi kuramayan diğer istekler kısa bir uyuma geçip önbellekten veri almayı yeniden dener; önbellekte hâlâ veri yoksa kilidi kurma işlemini tekrarlar; yaklaşık referans kod aşağıdaki gibidir.

```Python
data = redis_cli.get(key)
while not data:
    if redis_cli.setnx('mutex', 'x'):
        redis.expire('mutex', timeout)
        data = db.query(...)
        redis.set(key, data)
        redis.delete('mutex')
    else:
        time.sleep(0.1)
        data = redis_cli.get(key)
```

#### Önbellek Çığ (Cache Avalanche)

Önbellek çığ, veriyi önbelleğe koyarken aynı süre sonunun kullanılmasıdır; bu, önbelleğin belirli bir anda aynı anda geçersiz olmasına, isteklerin tümünün veritabanına yönlendirilmesine ve veritabanının anlık aşırı yükten çökmesine yol açar. Önbellek çığ sorununu çözmek de nispeten basittir; belirlenen önbellek süre sonuna rastgele bir süre ekleyerek farklı anahtarların aynı anda topluca geçersiz olması bir ölçüde önlenebilir. Bir başka yöntem de çok düzeyli önbellek kullanmaktır; her düzeydeki önbelleğin süre sonu farklıdır; böylece bir düzeydeki önbellek topluca geçersiz olsa bile diğer düzeylerdeki önbellek veri sağlayabilir; tüm isteklerin veritabanına düşmesi önlenir.
