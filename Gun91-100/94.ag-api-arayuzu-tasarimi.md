## Ağ API Arayüzü Tasarımı

> **Translated to Turkish by** himmetcanumutlu

Günümüzde birçok Web uygulaması ve mobil uygulama, ön-arka uç ayrımı geliştirme modelini kullanır; ön-arka uç ayrımı, kısaca ön ucun veya mobil ucun ağ API arayüzü aracılığıyla arka uçla etkileşime girmesi, arayüzde sağlanan veriyi alması ve kullanıcı arayüzünün render edilmesinden sorumlu olmasıdır. API, uygulama programlama arayüzünün kısaltmasıdır; ağ API'si genellikle bir URL (tekdüzen kaynak bulucu) üzerinden erişilebilen bir kaynağı ifade eder; yani bu URL aracılığıyla sunucudan belirli bir kaynak üzerinde işlem yapmasını isteyebilir ve işlemin sonucunu alabiliriz. Düşünebilirsiniz: Ağ API arayüzü de bir tür sarmalama (encapsulation) değil midir; kısacası karmaşık iş mantığını basit API arayüzünün içinde gizler.

URL'nin genel biçimi şöyledir:

```
protokol://kullanıcıadı:parola@ana bilgisayar:port/yol1/.../yolN/kaynak adı
```

> **Açıklama**: URL'deki kullanıcı adı (bazı durumlarda kullanıcı adı sağlamak gerekmez), parola (bazı durumlarda parola sağlamak gerekmez), port (bazı durumlarda varsayılan port kullanılır), yol (kaynak bazı durumlarda doğrudan kök yolda `/` bulunur) zorunlu parçalar değildir; gereksinime göre ayarlanabilir.

Ağ API'si genellikle HTTP veya HTTPS üzerinden erişilir; HTTP/HTTPS üzerinden erişimin en büyük avantajı, erişimin çok basit ve kolay olması ve diller arası, uygulamalar arası erişim ile birlikte çalışabilirlik sağlamasıdır.

### Tasarım İlkeleri

#### Kritik Sorunlar

Mobil uç veya PC ucu için ağ API arayüzü tasarlarken çok önemli bir ilke şudur: **API arayüzünü kullanıcı arayüzüne veya işlemlere göre değil, iş varlığına göre tasarlayın**. API arayüzünün tasarımı kullanıcının işlemlerine veya arayüzdeki işlev ayarlarına göre yapılırsa, gereksinimler değiştikçe kullanıcı arayüzü de ayarlanır, gereken veri de değişir; o zaman arka uç geliştiricisi sürekli API'yi ayarlamak veya bir API'nin birden çok sürümünü tasarlamak zorunda kalır; bunların hepsi projenin geliştirme ve bakım maliyetini artırır. İş varlığını, sunucunun sağladığı kaynak; URL'yi de kaynağın konumlayıcısı (tanımlayıcısı) olarak düşünebiliriz; bu yaklaşım en basit ve doğal olanıdır. Görece karmaşık kullanıcı işlemleri için bir "cephe" (tasarım desenlerindeki "cephe deseni") sağlayabiliriz; bu "cephe" aracılığıyla birden çok arayüzün işlevlerini birleştirmeniz yeterlidir.

Aşağıda belirli bir sitenin açık API arayüzü verilmiştir; API tasarımının iş varlığı etrafında yapıldığı ve hepsinde "adından ne işe yaradığı anlaşıldığı" görülebilir.

| Yorum              |                        |
| ----------------- | ---------------------- |
| comments/show     | Belirli bir gönderinin yorum listesini al |
| comments/by_me    | Kendi yorum listeniz   |
| comments/to_me    | Aldığınız yorumların listesi |
| comments/mentions | Sizi @'leyen yorumların listesi |
| comments/create   | Bir yorum oluştur       |
| comments/destroy  | Bir yorum sil           |
| comments/reply    | Bir yoruma yanıt ver    |

Belirtmek gerekir ki **yukarıdaki API arayüzleri REST tarzında değildir**. REST, bir ağ uygulama mimarisi tarzıdır; dağıtık ağ uygulamaları için en uygun olduğu düşünülür. REST hakkında bilgi için Ruan Yifeng'in [《RESTful Mimariyi Anlamak》](http://www.ruanyifeng.com/blog/2011/09/restful.html) ve [《RESTful API Tasarım Rehberi》](http://www.ruanyifeng.com/blog/2014/05/restful_api.html) yazılarını okuyabilirsiniz; elbette bu iki yazıyı da eleştirel biçimde okumalısınız; çünkü burada ifade edilen görüşler tamamen doğru değildir, hatta bazı içerikler kendiyle çelişir.

API arayüzünün döndürdüğü veriler genellikle **JSON** veya **XML** biçimindedir; XML veri biçimi günümüzde temelde kullanımdan kalkmıştır. JSON biçimindeki veriler için, `null` gibi değerler döndürmemeye dikkat etmeliyiz; çünkü böyle değerler doğru ele alınmazsa ön uç ve mobil uç geliştirmeye gereksiz sorunlar çıkarır (geliştirici güçlü tipli bir dil kullanıyor olabilir). Bu sorunu kaynağından çözmek için veritabanını tasarlarken her alana mümkün olduğunca "not null" kısıtı ekleyin veya makul varsayılan değer kısıtı belirleyin.

#### Diğer Sorunlar

1. Güncelleme bildirimi sorunu: Sistemi her kullanışınızda ilk erişilen bir API tasarlayın; bu API mobil uca sistem güncellemesiyle ilgili bilgileri döndürür; böylece kullanıcıların App'i güncellemesi sağlanabilir.
2. Sürüm yükseltme sorunu: API sürümü yükseltilirken düşük sürümle uyumluluk dikkate alınmalı; aynı zamanda hem yeni hem eski sürümün erişilebilir olması sağlanmalıdır; sürüm bilgisi URL'ye eklenebilir veya sürüm numarası HTTP(S) protokol başlığına konulabilir; bu konuda pek çok tartışma vardır; ilgilenenler [stack overflow](https://stackoverflow.com/questions/972226/how-to-version-rest-uris) üzerindeki tartışmaya bakabilir.
3. Görüntü boyutu sorunu: Mobil uç bir görüntü için farklı boyutlara ihtiyaç duyabilir; görüntüyü alırken boyut parametresi geçip karşılık gelen kaynağı alabilirsiniz; daha iyi bir yaklaşım, doğrudan bulut depolama veya CDN kullanmaktır (görüntü ölçekleme işlevini doğrudan sağlar); bu, kaynağa erişimi hızlandırır.

### Dokümantasyon Yazımı

Aşağıda yorum arayüzü tasarımı örneğiyle, arayüz dokümantasyonunun nasıl yazılması gerektiğini kısaca açıklıyoruz.

Önce küresel dönüş durum kodlarını tanımlayabiliriz.

| Dönüş kodu | Dönüş bilgisi     | Açıklama                               |
| ------ | ------------ | ---------------------------------- |
| 10000  | Yorum başarıyla alındı |  |
| 10001 | Yorum başarıyla oluşturuldu |  |
| 10002  | Yorum oluşturulamadı | Yorum, denetim mekanizmasını ihlal ettiği için oluşturulamadı |
| 10003 | Yorum silinmiş     | Yorum, uygunsuz içerik nedeniyle silinmiş |
| 10004 | …… | …… |

1. Makalenin yorumlarını alma.

   **GET** `/articles/{article-id}/comments/`

   Geliştirici: 王大锤

   Son güncelleme zamanı: 10 Ağustos 2018

   Etiket: v 1.0

   Arayüz açıklaması: Belirtilen makalenin tüm yorumlarını alır

   Kullanım yardımı: Varsayılan olarak 20 veri döndürür; istek başlığında kimlik tanımlayıcısı (key) ayarlanması gerekir

   İstek parametreleri:

   | Parametre adı | Tür   | Zorunlu mu | Parametre konumu | Açıklama                                 |
   | ------ | ------ | -------- | -------- | ------------------------------------ |
   | page   | tamsayı   | hayır       | sorgu parametresi | sayfa numarası, varsayılan 1                        |
   | size   | tamsayı   | hayır       | sorgu parametresi | her seferde alınacak yorum sayısı (10~100), varsayılan 20 |
   | key    | string | evet       | istek başlığı   | kullanıcının kimlik tanımlayıcısı                       |

   Yanıt bilgisi:

   ```JSON
   {
       "code": 10000,
       "message": "Yorum başarıyla alındı",
       "page": 1,
       "size": 10,
       "totalPage": 35,
       "contents": [
           {
               "userId": 1700095,
               "nickname": "王大锤",
               "pubDate": "31 Temmuz 2018",
               "content": "Editör hasta mı ne?",
               /* ... */
           },
           {
           	"userId", 1995322,
               "nickname": "白元芳",
               "pubDate": "2 Ağustos 2018",
               "content": "Yukarıdaki arkadaş iyi söylemiş",
               /* ... */
           }
       ]
       /* ... */
   }
   ```

2. Yeni makale yorumu ekleme.

   **POST** `/articles/{article-id}/comments`

   Geliştirici: 王大锤

   Son güncelleme zamanı: 10 Ağustos 2018

   Etiket: v 1.0

   Arayüz açıklaması: Belirtilen makale için yorum oluşturur

   Kullanım yardımı: Yok

   İstek parametreleri:

   | Parametre adı  | Tür   | Zorunlu mu | Parametre konumu | Açıklama       |
   | ------- | ------ | -------- | -------- | ---------- |
   | userId  | string | evet       | mesaj gövdesi   | kullanıcı ID'si     |
   | key     | string | evet       | istek başlığı   | kullanıcının token'ı |
   | content | string | evet       | mesaj gövdesi   | yorumun içeriği |

   Yanıt bilgisi:

   ```JSON
   {
       "code": 10001,
       "message": "Yorum başarıyla oluşturuldu",
       "comment": {
           "pubDate": "31 Temmuz 2018",
           "content": "Editör hasta mı ne?"
           /* ... */
       }
       /* ... */
   }
   ```



> **İpucu**: Arayüz dokümantasyonu yazma deneyiminiz yoksa, arayüz dokümantasyonu yazmak için çevrimiçi arayüz dokümantasyon düzenleme platformları olan [RAP2](<http://rap2.taobao.org/>) veya [YAPI](<http://yapi.demo.qunar.com/>) kullanılabilir.
